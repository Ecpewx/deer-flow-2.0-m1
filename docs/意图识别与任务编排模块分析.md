# DeerFlow 意图识别与任务编排模块分析

## 1. 概述

DeerFlow 的意图识别通过 **IntentPlanningMiddleware**（意图规划中间件）实现，它是一个 LangChain AgentMiddleware，在 LLM 执行前对用户输入进行**意图分析**、**对话状态追踪**和**动作决策**。

核心流程：

```
用户输入 → IntentPlanningMiddleware.before_model()
              ↓
          调用 LLM 进行意图分析（structured output）
              ↓
          {
            intent_card:      意图卡片（主意图、子意图、槽位等）
            conversation_state: 对话状态（阶段、已收集信息）
            action_decision:  动作决策（direct_answer / retrieve_then_answer / run_skill 等）
          }
              ↓
          注入 intent_planning_context（HumanMessage）到消息列表
              ↓
          Lead Agent LLM 执行
```

## 2. 位置与注册

### 2.1 注册位置

文件：`deer-flow-2.0-m1/backend/packages/harness/deerflow/agents/lead_agent/agent.py`

在 `_build_middlewares()` 函数中注册：

```python
# Mego: Add intent and planning
middlewares.append(IntentPlanningMiddleware())
```

### 2.2 中间件执行顺序

```python
# agent.py _build_middlewares() 中的顺序（从上到下执行）：
1. build_lead_runtime_middlewares()  # 基础运行时中间件（线程数据、上传、挂起工具调用等）
2. SummarizationMiddleware           # 摘要中间件（压缩长对话）
3. TodoMiddleware                    # 待办事项列表（plan mode）
4. TokenUsageMiddleware              # Token 用量追踪
5. TitleMiddleware                   # 对话标题生成
6. MemoryMiddleware                  # 长期记忆管理
7. IntentPlanningMiddleware          # ← 意图识别在这里！
8. ViewImageMiddleware               # 图片预览注入
9. DeferredToolFilterMiddleware      # 工具可见性过滤
10. SubagentLimitMiddleware          # 子 Agent 数量限制
11. LoopDetectionMiddleware          # 循环检测
12. ClarificationMiddleware          # 澄清请求拦截（最后一个）
```

**注意**：IntentPlanningMiddleware 在 ClarificationMiddleware 之前执行，所以在 LLM 真正运行之前就完成了意图分析。

## 3. 核心数据结构

### 3.1 IntentCardSchema（意图卡片）

```python
class IntentCardSchema(BaseModel):
    dialogue_relation: str     # continue_current_task | refine_current_task | switch_task | insert_question | unknown
    primary_intent: str        # knowledge_qa | learning_support | courseware_generation | ... | unknown
    sub_intent: str            # concept_explanation | concept_comparison | chapter_review | ... | general | unknown
    needs_retrieval: bool      # 是否需要检索知识库/课程资料
    needs_clarification: bool  # 是否需要追问澄清
    planning_mode: str         # none | single_step | multi_step
    user_goal: str             # 用户目标的文本描述
    confidence: float          # 分析置信度
    missing_slots: list[str]   # 缺失的槽位名称
    slots: dict                # 提取的槽位值
```

### 3.2 ConversationStateSchema（对话状态）

```python
class ConversationStateSchema(BaseModel):
    stage: str              # new | clarifying | executing | done
    dialogue_relation: str  # 同上
    active_intent: str      # 当前活跃意图
    last_user_goal: str     # 上一轮用户目标
    course_name: str        # 课程名称
    chapter: str            # 章节
    knowledge_points: list  # 知识点列表
    missing_slots: list     # 缺失槽位
    turn_count: int         # 对话轮次计数
```

### 3.3 ActionDecisionSchema（动作决策）

```python
class ActionDecisionSchema(BaseModel):
    action: str   # direct_answer | clarify | retrieve_then_answer | run_skill | multi_step_plan
    reason: str   # 决策理由
```

## 4. 意图分析过程

### 4.1 触发时机

`before_model()` / `abefore_model()` 在每个用户输入后、LLM 执行前被调用。

### 4.2 去重逻辑

通过 `_is_new_user_turn()` 检测是否是同一轮对话：

```python
def _is_new_user_turn(self, old_conversation_state, *, user_input, user_message_id):
    # 比较 message_id 或 user_input 是否变化
    # 如果不变则跳过（防止重复分析）
```

### 4.3 分析方式（两种）

#### 方式一：Structured Output（首选）

```python
model = create_chat_model(thinking_enabled=False)
structured_model = model.with_structured_output(IntentPlanningAnalysisSchema)
structured_response = structured_model.invoke(prompt)
```

使用 LangChain 的 `with_structured_output`，让 LLM 直接返回结构化的 JSON。

#### 方式二：纯文本 JSON 提取（fallback）

如果 structured output 失败，退化为纯文本输出，然后用正则提取 JSON。

#### 方式三：启发式 fallback（最终保底）

如果上述两种都失败，用 `_fallback_analysis()` 做简单关键词匹配。

### 4.4 分析 Prompt

```python
prompt = f"""
You are an intent recognition and task orchestration module for a university teaching
and research assistant system. Your job is NOT to answer the user.
Your job is to analyze the current user turn together with recent conversation history
and the previous conversation state. Return JSON only.

Decision rules:
1. continue_current_task / refine_current_task / switch_task / insert_question
2. needs_clarification=true 仅当缺少关键信息时
3. needs_retrieval=true 当需要课程资料/知识库时
4. planning_mode=multi_step 用于课件生成、评分等复杂任务
5. 不要回答用户的问题本身
...
"""
```

## 5. 动作决策类型

| action | 含义 | 使用场景 |
|---|---|---|
| `direct_answer` | 直接回答 | 简单问答，无需检索 |
| `clarify` | 需要追问澄清 | 信息不足，需要更多输入 |
| `retrieve_then_answer` | 先检索再回答 | 需要知识库/课程资料 |
| `run_skill` | 执行特定技能 | 调用已注册的技能 |
| `multi_step_plan` | 多步骤规划 | 课件生成、评分等复杂任务 |

## 6. 上下文注入机制

### 6.1 注入条件

```python
def _should_inject_context(self, intent_card, action_decision):
    return (
        action in {"multi_step_plan"}
        or needs_clarification
        or planning_mode in {"multi_step"}
    )
```

**只有 multi_step_plan 或需要澄清时才会注入上下文消息。**

### 6.2 注入内容

```python
<intent_planning_context>
dialogue_relation: continue_current_task
primary_intent: knowledge_qa
user_goal: 解释生态保护红线的概念
confidence: 0.95

<conversation_state>
{...}
</conversation_state>

<action_decision>
{"action": "retrieve_then_answer", "reason": "..."}
</action_decision>
</intent_planning_context>
```

### 6.3 消息类型

注入的消息是 **HumanMessage**（name="intent_planning_context"），这意味着 LLM 会把它当作"用户输入"的一部分来理解。

## 7. 已知问题与改进建议

### 7.1 问题 1：上下文注入类型不当

**现状**：`intent_planning_context` 是 HumanMessage。

**影响**：
- LLM 会把它当作"用户的额外输入"，可能干扰其对真实用户意图的判断
- 混在用户消息中，语义上不合适

**改进建议**：改为 SystemMessage 或 ToolMessage，或完全移除这种注入方式，改用 state 传递。

### 7.2 问题 2：旧上下文残留

**现状**：`_build_remove_old_context_ops()` 只在 `should_inject=True` 时才会清理旧 context 消息。

**影响**：当 `should_inject=False` 时（如 simple Q&A），旧的 context 消息不会被移除，持续累积在对话历史中。

代码中的清理逻辑：

```python
remove_ops = self._build_remove_old_context_ops(messages)
message_updates: list[RemoveMessage | HumanMessage] = list(remove_ops)

if should_inject:
    message_updates.append(
        self._build_intent_context_message(...)
    )
```

**改进建议**：不管 `should_inject` 是什么值，都应该清理旧的 context 消息。

### 7.3 问题 3：缺少工具可见性控制

**现状**：intent_planning 分析出 `needs_retrieval=True` 和 `action=retrieve_then_answer`，但这只是一个建议（注入的文本消息），LLM 可以选择忽略。

**影响**：
- LLM 可能绕过知识库直接去联网搜索
- 工具的描述（"优先使用"）只是软约束，LLM 不一定遵守

**改进建议**：
- 方案 A：在中间件层面根据 intent 动态过滤工具的可见性（如当 `needs_retrieval=True` 时，暂时隐藏 web_search 等工具）
- 方案 B：使用 `ToolChoice` / `tool_choice` 机制，强制 LLM 先调用 chroma_retrieve

### 7.4 问题 4：分析模型与主模型不同

**现状**：意图分析使用的是 `create_chat_model(thinking_enabled=False)`，与主 Agent 模型独立。

**优点**：意图分析可以用更便宜/更快的模型
**潜在问题**：如果两个模型能力差距大，分析质量可能不稳定

---

## 8. 改进计划

### 短期改进

1. **清理旧 context 消息**：在 `_build_remove_old_context_ops` 中不再依赖 `should_inject`，每次都清理旧的 intent_planning_context
2. **强化工具描述**：已对 `chroma_retrieve` 添加了明确的三步执行规则和优先级说明

### 中期改进

3. **上下文消息类型调整**：将 intent_planning_context 从 HumanMessage 改为 SystemMessage
4. **工具可见性过滤**：当 `needs_retrieval=True` 时，在 DeferredToolFilterMiddleware 中控制工具列表，优先暴露 chroma_retrieve

### 长期改进

5. **State 驱动代替注入**：完全移除消息注入，改用 state 字段传递意图分析结果，下游环节（prompt 模板、tool filter）直接读取 state
6. **支持多轮意图修正**：当 LLM 发现知识库结果不足时，可以回退到联网搜索，形成闭环

---

## 9. 与其他中间件的交互

| 中间件 | 与 IntentPlanning 的关系 |
|---|---|
| **DeferredToolFilterMiddleware** | 可以配合实现工具可见性控制（改进计划 4） |
| **ClarificationMiddleware** | IntentPlanning 分析出 `needs_clarification=True` 时，由 ClarificationMiddleware 拦截并追问 |
| **LoopDetectionMiddleware** | 防止意图分析后的工具调用进入死循环 |
| **TitleMiddleware** | IntentPlanning 在 TitleMiddleware 之后执行，所以可以访问到对话标题 |
| **SummarizationMiddleware** | IntentPlanning 在 SummarizationMiddleware 之后执行，所以历史已被压缩 |

---

## 10. 配置相关

所有模型配置通过 `deerflow/models.py` 的 `create_chat_model()` 创建，支持：

- thinking_enabled（是否启用思维链）
- reasoning_effort（推理努力程度）
- 模型名称解析（通过 `_resolve_model_name()`）

意图分析的 LLM 固定为 `thinking_enabled=False`，使用默认配置的模型。
